# Visual Iteration

Use when the user asks for visual quality, the acceptance list includes a visual condition, the requested change creates a related asset family, or the current presentation makes gameplay unreadable. Apply [player feedback](../principles/player-feedback.md). Do not turn every functional game task into an art pipeline.

1. Translate the visual requirements into concrete pass/fail conditions before editing. Check only applicable concerns: focal hierarchy, player/target/hazard distinction, action feedback, HUD legibility, composition, style consistency, motion, and requested viewport behavior. Freeze the conditions before the first capture. If inspection exposes a missing requirement, add it and recheck the affected captures. Never remove, merge, weaken, or reinterpret a failing condition to claim a pass. Change a frozen condition only when the user changes the requirement, then rerun its affected checks.
2. When the user gives no visual reference, set a short original direction from the brief and existing project: focal subject, palette, shape and type language, atmosphere, and camera. Use the project's current style and assets unless the user supplied a direction or requested a change. Reference images are optional and require user-provided or authorized material. Never require homage, a fixed number of screenshots, generated assets, or a particular tool.
3. For a requested family of related assets, define only the shared visual and technical constraints that affect use: view, palette, silhouette, in-game size, dimensions, transparency, frames, anchors, and import settings as applicable. Select one representative and validate it in the target game at intended scale and against its real background before producing the rest. Keep shared traits consistent across small batches; normalize through the project's existing tools and inspect dimensions, transparency, frame bounds, or anchors that matter to the asset. Inspect the family together, using a contact sheet when it helps, then check imported assets in the running game. Keep source and license provenance with the project assets. Skip this family workflow for logic-only work, one-off edits, or unrelated assets.
4. Capture the actual project in the target runtime, at the requested resolution and state. Preserve the same camera, viewport, theme, and relevant game state when comparing before and after.
5. Turn each visible defect into a concrete item: capture and region, observed problem, affected acceptance condition, and a condition that will show it is corrected. Correct hierarchy, spacing, contrast, alignment, clipping, inconsistent visual language, or unclear feedback directly. Avoid general instructions such as “make it more polished.”
6. Correct the most consequential related defects, then capture the same states and viewports again. Recheck every frozen condition against the final captures, including controls, status, collision cues, and accessibility signals.
7. When a distinct image-capable reviewer is actually available, give it the frozen conditions and current captures for a second read. Do not report an independent review when the author inspected the result alone.
8. Keep Playable and Visual as separate gates. Do not use a numeric aesthetic score, claim parity without an authorized reference and matching comparison conditions, or infer fun from a screenshot.

If repeated edits fail the same visual condition, question the layout, camera, asset, or rendering assumption before applying another cosmetic patch. Stop when the declared conditions pass or report the remaining defect and evidence gap; do not lower the bar to claim completion.
