# Player Feedback

The screen, sound, and controls are part of the mechanic. A rule is not usable merely because the code applies it.

- Give each important action a perceptible response that matches the resulting state: movement, hit, denial, cost, cooldown, progress, success, or failure.
- Put decision-relevant information where and when the player needs it. A hidden or late cue makes a correct rule feel arbitrary.
- Make the main goal, controllable actor, threats, and available action distinguishable at the target size. Establish one clear visual hierarchy; keep secondary HUD and decoration from competing with play.
- Keep the visual language coherent across scenes, controls, typography, palette, shape, and motion. Reuse the project's existing style unless the brief asks for a change.
- Do not communicate essential state by color alone. Preserve readable text, focus, and feedback for the input devices and accessibility needs in scope.
- Treat a screenshot as evidence for only the captured state and viewport. Judge timing, responsiveness, audio, input feel, and legibility in the running game where those claims matter.
- When the brief says beautiful but gives no style, choose a restrained, original direction that fits the genre and existing project; state the assumption and judge it against concrete conditions.

Prefer removing clutter and correcting hierarchy over adding decorative panels, particles, badges, or motion without a gameplay or communication purpose.
