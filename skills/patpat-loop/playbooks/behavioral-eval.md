# Behavioral Evaluation Playbook

Read [proof over proxy](../principles/proof-over-proxy.md) and [earned parallelism](../principles/earned-parallelism.md).

## Evidence-feasibility preflight

Before freezing the rubric, make one read-only pass over existing in-scope evidence:

1. **Coverage.** Map every material user requirement and safety constraint to a mandatory criterion. Optional checks are non-gating. If coverage is incomplete, name the gap, mark coverage `INCONCLUSIVE`, and do not freeze the rubric or claim an overall pass.
2. **Oracle and capture.** Name the observable oracle and existing evidence source per criterion (static evidence only for static requirements; no oracle = `INCONCLUSIVE`). For event-triggered or asynchronous criteria, distinguish a product deadline from the evaluator's observation window. Timing claims need a documented or user-approved bound (else `INCONCLUSIVE`). Otherwise predeclare one practical observation window as a capture budget (not a product promise); no event within it is `INCONCLUSIVE`, not `FAIL`. Never extend or poll the window during the same trial.
3. **Capability and authority.** For local-only criteria, inspect path and artifact access. For host/provider criteria, inspect tool registration, connection, exact operation/schema, and authorization separately using existing inspectable metadata. Record the grant or policy and its scope when authority is required. Reuse one current receipt per host/session unless binding changes. Presence, connection, credentials, or descriptions alone do not prove authorization, schema compatibility, or execution. If operation/schema metadata is not inspectable, mark only the dependent criterion `INCONCLUSIVE`. If live provider access is required and no approved read-only evidence establishes connection, record connection as `UNKNOWN` and the dependent criterion as `INCONCLUSIVE`; never probe a provider during preflight. Distinguish model-host transport from calls to the provider under test; report only what receipts prove and do not claim zero network activity without transport evidence.
4. **Isolation.** For independent state, record the already-approved surface and scope (host, project/provider, state, allowed actions, side effects). Verify with inspectable evidence that the current session is bound to that exact isolated target. A package copy or Git worktree does not prove independent provider state. If approval, its scope, or the current target binding is missing or ambiguous, do not run the dependent criterion; do not create a canary or disposable provider state to make it feasible.
5. **Candidate identity.** For claims about a candidate skill, verify with inspectable path and hash receipts that the actual loaded skill and relevant guidance bytes match the candidate; a hash of the repository copy alone does not prove the loaded bytes. If source identity is missing, mismatched, or uninspectable, mark candidate attribution `INCONCLUSIVE` and skip only that candidate-specific trial.
6. **Preflight status.** Use only `READY` or `INCONCLUSIVE` at preflight. `READY` is not a behavioral `PASS`. `UNKNOWN` describes a fact, not a status. Report per material criterion (not per evidence field), including only applicable facts and reusing current receipts. When a required fact is missing, mark only its dependent criterion `INCONCLUSIVE`, record the gap once, skip it for this run, and continue independent safe checks. Treat `INCONCLUSIVE` as terminal for that criterion in this run: do not repeat the same check, broaden the search, poll, probe, or ask the same question again. Reopen only after new inspectable evidence or a material change to scope, host, connection, contract, or candidate source. Trial verdicts remain `PASS`, `FAIL`, or `INCONCLUSIVE` under the frozen oracle.

For preflight-only requests, report one compact result referencing existing evidence and stop before routing or trials (no prompts, events, or retries). A request for another report alone does not reopen an `INCONCLUSIVE` criterion: reuse its prior receipt/status if available; otherwise report that it is unavailable and keep the criterion `INCONCLUSIVE` without repeating the same check.

## Paired comparisons of skill effects

Use paired comparisons only when claiming a skill revision or set improves behavior (standalone conformance needs no baseline). Before either arm, freeze: comparison claim, baseline, prompt/inputs, task set and pair count, alpha, rubric, oracle, criterion priority, hard safety constraints, and pair decision rule.

- **New skill or set:** compare candidate set vs same context without those target skills (keep shared repo/host policy unchanged; do not call it "without Patpat" unless all Patpat policy is absent).
- **Skill revision:** compare exact prior revision vs exact candidate revision.
- **Composition-specific claim:** compare candidate composition vs strongest relevant single skill or existing composition.

Match prompt/input bytes, repo/artifact snapshot, host/profile/version, model/settings, tools/schemas, permissions, context, and budgets wherever inspectable. Record per-arm loaded-skill inventories and hashes (including target absence or prior-revision hashes); never infer from repo contents, prompt, or package listing. Isolate arms from each other's context, artifacts, rubric, expected outcome, and transcript; run sequentially unless isolation holds.

Predeclare task sensitivity: ≥1 required criterion must exercise the target capability with a distinguishing oracle (else report incremental effect `INCONCLUSIVE`, not `TIE`). Record each arm's delivery mode (`source-injected content`, `explicit invocation`, or `native host routing`) plus loaded skill paths/hashes. `source-injected content` proves supplied-content claims only; `explicit invocation` does not prove natural discovery; routing claims require a natural trigger and host routing evidence. For content-effect claims, verify non-skill surfaces (prompt, inputs, repo, memory, host context) do not leak target content to baseline; uninspectable surfaces make content attribution `INCONCLUSIVE`.

Score each arm separately against the frozen oracle/rubric (`PATPAT_BETTER`, `BASELINE_BETTER`, `TIE`, or `INCONCLUSIVE`) using a predeclared total pair decision rule where hard safety violations cannot be outweighed. Control mismatches, unproven inventories, missing oracle evidence, or an inconclusive arm make the pair `INCONCLUSIVE`. Never rerun a valid failed arm to change its verdict; a corrected candidate starts a new pair.

For paired trials with judgment-based criteria, use a separate authorized reviewer as an optional blind adjudicator. Give them both arms' outputs and the evidence needed to judge them in one packet, with randomized `A`/`B` labels and arm/model identifiers removed from metadata. The reviewer sees the same frozen rubric and scores each arm independently in one pass before unblinding. Keep the A/B mapping outside the packet until both scores are frozen. Preserve action and effect evidence needed for safety review; if the prompt, rubric, output, or required evidence reveals arm identity, record the review as unblinded. Use only a reviewer authorized to access the complete packet under the project's data-handling scope; do not send private repository content or transcripts to an external reviewer without explicit authorization. If no suitable reviewer or safe masking is available, use the frozen oracle and rubric and report `unblinded`; report reviewer independence separately and do not claim a blind review. Record whether the reviewer was separate from the trial executors and whether its model family differed. Blind judgment supplements, but never replaces, deterministic oracles or the hard safety veto.

Report every pair and criterion result plus summary counts without pooling away failures. Small sets support claims only about observed tasks. Report time/token deltas only from comparable host receipts (else unavailable), reusing the receipts below.

## Judges, uncertainty, and the failure flywheel

- **Deterministic oracles first.** Use binary/deterministic checks wherever possible. Reserve model judges for genuine judgment (clarity, tone, usefulness), split into task-specific binary checks (never a single 1–5 holistic score). Accountable human scoring needs no calibration.
- **Calibrate gating model judges.** Before a model judge (or blind adjudicator) gates `PASS`, pair verdict, or promotion, calibrate each gating check separately against frozen human anchors (≥3 `PASS`, ≥3 `FAIL`, excluded from judge prompt) using:
  `python3 <patpat-eval skill directory>/scripts/eval_stats.py agreement --a <judge labels> --b <anchor labels> --min-kappa <frozen bar>`
  Default bar: Cohen's kappa ≥0.6 on ≥10 anchors (with two humans, resolve into one agreed set first and use `max(0.6, inter-human agreement)`; human agreement <0.6 means the check is ill-defined and must be rewritten). Uncalibrated or `INCONCLUSIVE` judges stay advisory only. Recalibrate on fresh held-out anchors after changing judge prompt, model, check wording, or task distribution; never tune a candidate against an uncalibrated judge.
- **Treat comparisons as estimates.** Cite rates as `k/n` with Wilson 95% CI via `eval_stats.py rate` (descriptive only). Overall `PATPAT_BETTER` / `BASELINE_BETTER` across pairs requires the exact sign test (`eval_stats.py pair`, `CANDIDATE_BETTER` → `PATPAT_BETTER`) clearing predeclared alpha (default `0.05`) on the frozen set (new pairs form a separate test). Ties carry no direction; exclude `INCONCLUSIVE` pairs from counts but report them beside the result (if they exceed the predeclared share or skew to one arm, overall result is `INCONCLUSIVE`). Claims cover only the sampled population; if planned pairs `< min_discordant_for_any_verdict`, state before running that no overall verdict is reachable. Never switch skills/models/prompts on descriptive or `INCONCLUSIVE` results, and statistics never override hard safety vetoes or failed mandatory criteria.
- **Failure flywheel.** Add privacy-safe regression cases from real escaped failures with frozen expected behavior. Between runs (never mid-run), move consistently passing cases to a regression tier (guarding regressions, excluded from comparison claims) and track escaped-failure origin.

## Trial execution and receipts

1. Declare capability, failure conditions, and rubric before trials.
2. Prepare one positive trigger, one neighboring negative trigger, and a representative task when practical.
3. Use the user-authorized project or pre-approved isolation surface (never create a canary/disposable project). Keep candidate/eval/test/judge/rubric vocabulary out of candidate-visible paths and prompts.
4. Run trials blinded to expected conclusion, rubric, and other arms. Hash exact prompts and frozen rubric before execution; bind prompt receipts to invocation command/host receipts (redact secrets into privacy-safe versions and limit completeness claims accordingly); preserve raw event stream/transcript at an inspectable path bound by digest.
5. Inspect artifacts, commands, evidence, cleanup, and scope. Verify post-cleanup receipt readability and digests once (`INCONCLUSIVE` on mismatch; do not rerun solely to recreate receipts).
6. Score against the rubric, not self-reports. On missing/contradictory live results, check observer/session health once via safe existing evidence (never probe provider); if unresolved, mark affected criterion `INCONCLUSIVE` and stop. After fixing a concrete verifier defect, rerun only the invalidated check once. Never repeat a valid target trial to overwrite a failure.
7. Separate verifier/environment limitations from skill defects.
8. Promote, revise, or reject based on observed behavior.

For stochastic/routing behavior, predeclare a bounded repeat count and expected result per prompt (do not increase mid-run). If independent trials cannot run safely in an approved surface, run non-mutating cases only and mark repeat-rate claims `INCONCLUSIVE`. Report trigger counts/rates for routing criteria and pass counts/rates per behavioral criterion; keep repeats sequential unless inputs and state are independently isolated.

Each behavioral criterion's frozen rubric must name an observable oracle (literal expected value, material side effect, awaited async result, or independently derived invariant); missing oracle = `INCONCLUSIVE`. Classify evidence as static only for inherently static requirements. Supervise adherence to the opinionated process specification across execution rather than accepting un-governed outcome flukes.

Live-agent receipts must record (reusing per host/session until binding changes): host and relevant version, Patpat revision + hashes of uncommitted candidate skill/references, pre-trial frozen rubric, prompt artifact paths/digests, tool operation/schema metadata paths/digests, actual loaded skill/guidance paths/hashes (attribution requires hash match; for paired arms, retain both inventories/hashes; uninspectable metadata/bytes = `INCONCLUSIVE` for that claim), raw event-stream/transcript path/digest, before/after artifacts/commands, cleanup, and verdict. Missing raw evidence = `INCONCLUSIVE`; receipts from another revision or host are stale.

Judgment failure classes are instruction-contract checks, not live-agent behavioral proof. Rubric examples: unnecessary questions, unnecessary planning, unnecessary artifacts, unnecessary fan-out, unnecessary abstraction, over-rigor on simple work, under-escalation on risky work, proxy proof, symptom patches, ignored architecture friction, context-window waste, and crossed authority (covering unnecessary ask vs inspect, over-plan, over-fan-out, over-rigor on trivial work, under-rigor on auth, proxy vs authoritative surface, and local-only vs delivery).
