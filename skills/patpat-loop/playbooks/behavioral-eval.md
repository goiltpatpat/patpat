# Behavioral Evaluation Playbook

Read [proof over proxy](../principles/proof-over-proxy.md) and [earned parallelism](../principles/earned-parallelism.md).

## Evidence-feasibility preflight

Before freezing the rubric, make one read-only pass over existing, in-scope evidence:

1. **Coverage.** Map every material user requirement and safety constraint to a mandatory criterion. Optional checks are non-gating and cannot cover a missing requirement. If coverage is incomplete, name the uncovered requirement, mark coverage `INCONCLUSIVE`, and do not freeze the rubric or claim an overall pass.
2. **Oracle and capture.** Name the observable oracle and existing evidence source for each criterion, including expected result or bounds when defined. Use static evidence only for static requirements; a criterion with no observable oracle remains `INCONCLUSIVE`. For event-triggered or asynchronous criteria, distinguish a product deadline from the evaluator's observation window. If timing is part of the claim, use a documented or user-approved bound; without one, that timing claim is `INCONCLUSIVE`. Otherwise predeclare one practical observation window as a capture budget, not a product promise; no event within it is `INCONCLUSIVE`, not `FAIL`. Never extend or poll the window during the same trial.
3. **Capability and authority.** For local-only criteria, inspect path and artifact access. For criteria requiring a host or provider operation, inspect tool presence and registration, connection, exact operation and schema, and authorization as separate facts using existing inspectable metadata. Record the grant or policy and its scope when authority is required. Reuse one current receipt across criteria in the same host/session; refresh it only when its binding changes. Tool presence, connection, credentials, or an agent-visible description alone do not prove authorization, compatible schema, or successful execution. If operation/schema metadata is not inspectable, mark only the dependent criterion `INCONCLUSIVE`. If live provider access is required and no approved read-only evidence establishes connection, record connection as `UNKNOWN` and the dependent criterion as `INCONCLUSIVE`; never probe a provider during preflight. Distinguish model-host transport from calls to the provider under test; report only what receipts prove and do not claim zero network activity without transport evidence.
4. **Isolation.** If a criterion needs independent state, identify the already-approved surface and record the approval source and scope, including host, project or provider, data/state, allowed actions, and side effects. Verify with inspectable evidence that the current session is bound to that exact isolated target. Approval of isolation does not authorize actions outside that scope. A package copy or Git worktree is not proof of independent provider state. If approval, its scope, or the current target binding is missing or ambiguous, do not run the dependent criterion; do not create a canary or disposable provider state to make it feasible.
5. **Candidate identity.** For claims about a candidate skill, verify with inspectable path and hash receipts that the actual loaded skill and relevant guidance bytes match the candidate; a hash of the repository copy alone does not prove the loaded bytes. If source identity is missing, mismatched, or uninspectable, mark candidate attribution `INCONCLUSIVE` and skip only that candidate-specific trial.
6. **Preflight status.** Use only `READY` or `INCONCLUSIVE` at preflight. `READY` means the criterion has its required evidence path, applicable authority and connection, any required isolation and current-session binding, and candidate identity when attributing a trial to a candidate; it is not a behavioral `PASS`. `UNKNOWN` describes a fact, not a status. The material criterion is the reporting unit, not each evidence field; include only applicable facts and reuse current receipts. When a required fact is missing, mark only its dependent criterion `INCONCLUSIVE`, record the gap once, skip it for this run, and continue independent safe checks. Treat `INCONCLUSIVE` as terminal for that criterion in this run: do not repeat the same check, broaden the search, poll, probe, or ask the same question again. Reopen it only after new inspectable evidence or a material change to the approved scope, host, connection, contract, or candidate source. Trial verdicts remain `PASS`, `FAIL`, or `INCONCLUSIVE` under the frozen oracle.

If the user requests preflight only, report one compact result and stop before routing or behavioral trials. Reference existing evidence instead of copying it into duplicate receipts. Do not create prompts, deliver events, or run trials. A missing item is not an automatic retry; start another run only after the evidence or scope materially changes. A request for another report alone does not reopen an `INCONCLUSIVE` criterion: reuse its prior receipt/status if available; otherwise report that it is unavailable and keep the criterion `INCONCLUSIVE` without repeating the same check.

1. Declare the capability, failure conditions, and scoring rubric before trials.
2. Prepare one positive trigger, one neighboring negative trigger, and a representative task when practical.
3. Use the user-authorized project. Use only an already-approved isolation surface when independent state is necessary; do not create a canary or disposable project solely for evaluation. Keep candidate, eval, test, judge, and rubric vocabulary out of candidate-visible paths and prompts.
4. Run trials without revealing the expected conclusion, scoring rubric, or another candidate's output. Preserve each exact prompt and the frozen rubric in inspectable, access-controlled receipts and hash them before execution. Bind each prompt receipt to the invocation with the recorded command or host receipt showing the bytes used. Keep secrets out of receipts; if the full prompt cannot be retained safely, record a privacy-safe version and limit completeness claims to what can be reviewed. Preserve the raw event stream or transcript at an inspectable path and bind it by content digest.
5. Inspect resulting artifacts, commands, evidence, cleanup, and scope control. After cleanup, verify once that required receipts remain readable and match their recorded digests; if not, mark affected claims `INCONCLUSIVE` and do not rerun work only to recreate receipts.
6. Compare results against the declared rubric; do not score self-reports. If a live result is missing or contradictory, check observer/session health once using existing safe evidence; never probe the provider for this check. If unresolved, mark only the affected criterion `INCONCLUSIVE` and stop. After a concrete verifier defect is fixed, rerun only the invalidated check once; if it still fails, classify the blocker and stop. Never repeat a target trial to overwrite a valid failure; a corrected candidate is a new trial.
7. Record verifier or environment limitations separately from skill defects.
8. Promote, revise, or reject the change based on observed behavior.

For routing-sensitive or otherwise stochastic behavior, predeclare a bounded repeat count and expected result per prompt; do not increase it after seeing results in the same run. If equivalent independent trials cannot be run safely in an approved surface, run only non-mutating cases and mark repeat-rate claims `INCONCLUSIVE`. Report trigger counts and rates only for routing criteria; report pass counts and rates per behavioral criterion for other tasks. A single pass proves only that trial, and aggregate rates are descriptive: never hide or relabel a failed run as passing. Keep repeats sequential unless every run has independently isolated inputs and state.

The frozen rubric must name the oracle for each behavioral criterion: returned value, changed state, emitted effect, or bounded invariant. Use a literal expected result for deterministic output, the material effect for void or side-effect-only work, an awaited result for async work, and an independently derived invariant for nondeterministic work. A behavioral criterion that cannot name an observable oracle is invalid and the trial is `INCONCLUSIVE`; classify evidence as static only when the requirement itself is static from the outset.

Live-agent receipts must record host and relevant version once per session, Patpat revision plus hashes for any uncommitted candidate skill or reference, the rubric frozen before execution, exact prompt artifact paths and digests, and relevant tool operation/schema metadata paths and digests. Reuse current receipts across criteria bound to the same host/session; refresh only after a material binding change. Record the actual loaded skill and guidance paths and hashes; attribute direct invocation to the candidate only when loaded hashes match the candidate. If the host cannot expose the loaded bytes or required tool/schema metadata, state that and keep only the corresponding claim `INCONCLUSIVE`; do not infer it from another profile or from the candidate source. A claim that metadata was available is not a substitute for its receipt. Record the raw event-stream or transcript path and digest, before/after artifacts and commands (not self-report), cleanup, and verdict. Missing raw evidence is `INCONCLUSIVE`; a receipt from another revision or host is stale.

Judgment failure classes are instruction-contract checks, not live-agent behavioral proof. Rubric examples: unnecessary questions, unnecessary planning, unnecessary artifacts, unnecessary fan-out, unnecessary abstraction, over-rigor on simple work, under-escalation on risky work, proxy proof, symptom patches, ignored architecture friction, context-window waste, and crossed authority. Include instruction-contract examples for unnecessary ask versus inspect, over-plan, over-fan-out, over-rigor on trivial work, under-rigor on auth, proxy versus authoritative surface, and local-only versus delivery.
